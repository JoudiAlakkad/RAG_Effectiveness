# Measuring the Effectiveness of Retrieval-Augmented Generation (RAG)

> **Programming for Modern Machine Learning --- February 2025**\
> **Authors:** Joudi Alakkad

## Overview

Retrieval-Augmented Generation (RAG) is a method for providing Large
Language Models (LLMs) with relevant external context before generating
a response.

This project investigates the effectiveness of a RAG pipeline by
comparing LLM responses **with RAG** against responses generated by
**classical LLM queries without RAG**.

The central question is:

> **Does retrieving relevant external context improve the quality of an
> LLM's answers?**

The project evaluates this question using both automatic metrics and
human evaluation.

------------------------------------------------------------------------

## Motivation

Classical LLMs have several limitations:

-   **Knowledge limitations:** a model's knowledge is bounded by its
    training data, which can make access to up-to-date or
    domain-specific information difficult.
-   **Hallucinations:** LLMs can produce factually incorrect statements
    due to limitations in their available knowledge.
-   **Context sensitivity:** models may struggle to effectively retrieve
    and use task-specific information.

One possible solution is **fine-tuning**, where a pretrained model is
further trained on task-specific data. However, the presentation
identifies important disadvantages:

-   Retraining can be expensive and time-consuming.
-   Domain-specific information becomes part of the model itself.
-   The resulting knowledge is relatively static and therefore less
    flexible.

RAG provides an alternative by allowing relevant external information to
be retrieved at query time.

------------------------------------------------------------------------

## What is RAG?

RAG is a framework for improving language-model performance by providing
an LLM with relevant information retrieved from an external database.

The approach offers:

-   **Real-time context updates**
-   **Scalability**
-   **Flexibility**
-   Retrieval of information without retraining the underlying LLM

### RAG Pipeline

The implemented workflow follows these main steps:

``` text
Documents
    │
    ▼
Embeddings Model
    │
    ▼
Vector Database
    │
    │   User Query
    │       │
    │       ▼
    └──► Similarity Search
            │
            ▼
      Relevant Context
            │
            ▼
     Query + Context
            │
            ▼
           LLM
            │
            ▼
    Generated Response
```

### 1. Document processing

External documents are passed through an embeddings model and
represented in a form suitable for similarity search.

### 2. Query

A user submits a question to the system.

### 3. Retrieval

The vector database is searched for context chunks that are similar to
the user's query.

### 4. Context augmentation

The retrieved context is combined with the original user query to
construct the prompt.

### 5. Generation

The LLM generates a response based on the augmented prompt.

## Retrieval Quality

The quality of retrieval is an important factor in the overall
effectiveness of a RAG system.

The presentation identifies several factors that influence retrieval
quality:

-   Quality of the available context
-   Vector-database configuration
-   Chunk size
-   Chunk overlap
-   Choice of embeddings model

The project therefore treats retrieval as an important part of the
evaluation rather than assuming that adding a RAG pipeline automatically
produces better answers.

------------------------------------------------------------------------

## Generation Quality

The quality of the generated response also depends on several factors:

-   Model parameters such as **temperature**
-   Prompt design
-   Quality of the retrieved context
-   Choice of generation model

The experiments therefore compare different generation configurations
with and without retrieved context.

------------------------------------------------------------------------

## Latency

RAG introduces additional computational work because the system must
retrieve relevant context before generating an answer.

The presentation identifies this additional computation as a source of
latency.

A proposed solution is to run the workload on GPU infrastructure, for
example using:

-   Google Colab
-   Kaggle

# Evaluation

The main objective of the evaluation is to measure the impact of the RAG
pipeline on answer quality compared with the same language model
operating without RAG.

The project uses four evaluation approaches:

1.  **BERTScore**
2.  **ROUGE**
3.  **BLEU**
4.  **Human evaluation**

------------------------------------------------------------------------

## BERTScore

BERTScore measures semantic similarity using contextual embeddings from
BERT.

It calculates:

-   Precision
-   Recall
-   F1-score

The F1-score is the harmonic mean of precision and recall.

### What it measures

**Semantic similarity** between the generated response and the reference
answer.

------------------------------------------------------------------------

## ROUGE

ROUGE measures the overlap between generated and reference text.

The project considers:

-   **ROUGE-1:** overlap of unigrams
-   **ROUGE-2:** overlap of bigrams
-   **ROUGE-L:** based on the longest common subsequence (LCS)

### What it measures

**N-gram overlap** between the generated response and the reference
answer.

------------------------------------------------------------------------

## BLEU

BLEU evaluates generated text using n-gram precision.

The metric also uses a **brevity penalty**, which prevents very short
predictions from receiving disproportionately high scores.

### What it measures

**N-gram precision while accounting for overly short predictions.**

------------------------------------------------------------------------

## Human Evaluation

Automatic metrics are complemented by human evaluation.

Human evaluators compare generated predictions with reference answers
based on **semantic accuracy**.

This provides an additional perspective on response quality beyond
purely automatic text-similarity metrics.

------------------------------------------------------------------------

# Results

The experiments presented in the accompanying presentation show a
consistent improvement when RAG is used.

Across the presented evaluation charts:

-   **BERTScore:** RAG produces higher scores for both evaluated models.
-   **ROUGE:** RAG produces higher ROUGE-1, ROUGE-2, and ROUGE-L scores.
-   **BLEU:** RAG produces higher BLEU scores for both evaluated models.
-   **Human evaluation:** responses generated with RAG receive
    substantially higher evaluation scores than responses without RAG.

The final comparison presented in the project combines the evaluation
dimensions into an overall view of model performance. The radar chart
shows the RAG configuration outperforming the corresponding non-RAG
configuration across the evaluated dimensions.

### Overall conclusion

The experimental results support the project's central hypothesis:

> **Providing relevant retrieved context improves the quality of
> LLM-generated answers compared with querying the LLM without RAG.**

At the same time, the project highlights that RAG performance depends on
the quality of retrieval, the retrieved context, model configuration,
and computational resources.

## Challenges Identified

### Retrieval quality

Retrieval quality depends on:

-   Context quality
-   Chunk size
-   Chunk overlap
-   Embeddings model

### Generation quality

Generation quality depends on:

-   Temperature
-   Prompt design
-   Retrieved context
-   Generation model

### Latency

The additional retrieval step creates computational overhead. GPU
execution is suggested as a way to reduce the practical impact of this
overhead.
